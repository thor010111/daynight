# Generate a dynamic wallpaper

Start with three smaller concept images and choose a direction with the user before creating the native 4K master. Then edit the master's lighting for each time of day. In generation prompts, require the master scene's camera, geometry, objects, materials, textures, and composition to stay fixed. Judge returned edits by the perceptual acceptance standard below. The user prefers AI relighting with visual checks over scripted color grading.

Treat matching as an acceptance requirement, not a capability guaranteed by prompting. AI edits can change details. Never claim pixel-exact geometry or automatic proof of consistency; report what was actually inspected. If distracting drift remains, the set is unfinished.

## Perceptual acceptance standard

The default is **“no distracting drift at normal desktop size.”** Compare the whole image and transitions at the intended desktop display size and an ordinary viewing distance. If that display is unavailable, use a representative full-frame preview, record its dimensions, and state the reduced review coverage. A thumbnail alone is insufficient.

Allow minor differences in foliage, plaster texture, window detail, or small roof fixtures when they do not distract at desktop scale or cause noticeable jumps between times. Use native-size crops, overlays and blink to diagnose differences; a discrepancy found at 100% zoom is not by itself a rejection. Record accepted minor drift in `review.md` rather than claiming that no differences exist. Do not spend retries correcting differences that already meet this standard.

Reject noticeable camera/crop/scale movement, changed building outlines, pool/terrain or major-tree displacement, conspicuous added or missing objects, style changes, and distracting transition flicker. This tolerance does not relax coherent lighting/shadow progression or technical requirements such as exact frame dimensions. Apply stricter matching when the user explicitly requests it.

Moonlit nights are always an allowed default; do not require separate approval merely because a night frame has pronounced directional shadows. Plan and record a plausible camera-relative moon direction/elevation, including an off-frame moon, and check shadows and illuminated faces against it. Unless a real location/date or a moonless night is requested, an artistic moonlit interpretation is acceptable. Night shadows need not disappear or differ from noon when the planned moon position produces a similar direction; that similarity alone is not a lighting failure. Judge nighttime exposure, warm local lights and overall night appearance separately, and still reject contradictory light directions or a night that reads as bright daylight.

## Establish the scene

Use the user's prompt, reference, dimensions, schedule, and destination. Infer macOS HEIC when working in the daynight repository. Otherwise ask about the platform only if it affects the deliverable. Default to a landscape 16:9 scene and six frames: night 00:00, dawn 06:00, morning 09:00, noon 12:00, sunset 18:00, and blue hour 20:00. These are editable clock times, not calculated sunrise/sunset times.

State the chosen schedule, initial `1K` concept tier, and final `4K` resolution before generation. Use the intended final aspect ratio for concepts, defaulting to `aspect_ratio: "16:9"`. After selection, use Nano Banana Pro's native `resolution: "4K"` preset for the master and every relighting edit, then measure and report the returned pixel dimensions; a preset does not promise exact 3840 × 2160. If the user supplies exact final pixels, first check whether the endpoint supports them. If it does not, explain that limitation and obtain agreement to the native preset before generation. Do not invent exact-size support or switch models to satisfy a size request. For the default landscape preset, reject final output below 3840 × 2160 rather than treating the requested 4K label as proof. The smaller concepts are for direction selection only; do not upscale, resize, or crop them into final frames.

Once the native master is measured and accepted, lock its exact pixel dimensions for all edits and checks. Do not also demand an exact aspect ratio that conflicts with them: an accepted 1672 × 941 canvas, for example, is only approximately 16:9. A one-pixel mismatch still requires a retry or an explicitly agreed change; stronger prompt wording does not guarantee size control.

Create a fresh output folder, usually `output/wallpapers/<scene>/`, without replacing an existing set. Keep the three concepts and their prompts in `concepts/`, alongside the later master, accepted frames, prompts, review notes, comparison page, manifest, and final HEIC. Retain failed attempts separately from accepted frames.

## Generate three concepts and select a direction

Use **Nano Banana Pro (`google/gemini-3-pro-image`) through OpenRouter** for all concepts, the master, every relighting edit, and every retry. Read [references/openrouter.md](references/openrouter.md) before generation for authentication, supported resolution settings, image references, response decoding, and transport limits. Load `OPENROUTER_API_KEY` from the repository-root `.env` when it is not already exported; never display its value. This skill uses that API directly; built-in image generation and upscaling are not part of this workflow. Keep this model fixed throughout the run. Do not use another model as a fallback unless the user explicitly requests it. If `OPENROUTER_API_KEY` or API access is unavailable, report the blocker and preserve completed work.

Use [references/prompts.md](references/prompts.md) to create three meaningfully different interpretations of the requested scene at native `resolution: "1K"`. Make three separate requests with `n: 1`, each producing one full-frame image. Vary composition, viewpoint, or visual treatment within the user's constraints; keep comparable daytime lighting so these are alternative directions, not three times of day. Preserve requested subjects and style. Inspect and save each concept's original bytes, decoded PNG, prompt, measured dimensions, and available usage/cost under distinct names such as `concepts/01.png` through `03.png`.

Show all three images individually with numbered labels and a short explanation of their differences. Recommend the strongest direction based on the brief, desktop composition, and suitability for relighting, then ask the user which concept to develop and whether to adjust it. Stop here until the user selects a direction; do not generate the 4K master, time-of-day set, or package while waiting. Record the selection and requested adjustments in `review.md`. If none fits, use the user's feedback for another small concept round before proceeding. Skip this stage only when the user explicitly asks to skip concepts or has already selected a supplied concept; an existing final master can proceed directly to relighting.

## Generate and lock the master

Generate a fresh native 4K master using the selected concept as an image reference and the selected prompt plus requested adjustments. Use the reference transport in [references/openrouter.md](references/openrouter.md). Preserve the chosen direction and composition while generating native detail; do not enlarge the concept locally or use its small dimensions as the final canvas. Inspect the master against the selected concept for adherence to the chosen direction before deriving frames. If it materially departs, retry with a targeted correction, up to two retries, then preserve the work and report the unresolved difference. Favor clear daytime lighting that exposes detail for inspection. Generate one full-frame image, never a collage of times of day. Do not remove user-requested scene elements merely to simplify matching.

Inspect the master before deriving frames. Save the provider's original bytes and decode them into the output folder as `master.png`; Nano Banana may return JPEG even when PNG was requested. Convert the format without resizing, cropping, grading, or changing composition; do not merely rename a non-PNG file. Use the master itself for the matching daytime slot when appropriate. Record its SHA-256 and measured dimensions, model, requested API resolution/aspect ratio, available usage/cost, the original user prompt, the generation prompt, and the scene constraints in `review.md`. Keep credentials and inline image data out of review notes.

Make a short scene-specific list of landmarks visible in the master: horizon height, building corners, window count, mountain ridges, tree silhouettes, paths, foreground objects, and distinctive texture details. Use locations or approximate image coordinates to make later comparison concrete. Also record the allowed lighting changes and a coherent sun/shadow trajectory. Freeze weather, cloud shapes, vegetation, water surface geometry, season, and material patterns; changing the clock alone does not authorize changing these.

Before locking the master, check its actual illumination against the planned daytime sun direction; the prompt alone is not evidence. Record a camera-relative sun direction/elevation and expected shadow direction/length for each phase, grounded in the scene orientation and season. Use calculated positions when a real location/date is required; otherwise identify the plan as artistic. Select at least two visible lighting landmarks, such as a chimney's cast shadow, a tree's ground shadow, or differently oriented building faces, with approximate image coordinates. Resolve a master/plan mismatch before deriving frames. Do not assume morning and evening shadows must reverse on screen: the expected movement depends on the chosen sun path and camera.

The concept selection is the default user decision point. Do not require a second approval of a faithful 4K master unless the user asks for one. Once accepted, keep the master immutable. If the master must change, invalidate and regenerate its derived frames.

## Relight from the same source

Generate each time of day as an **edit of the original master**. Never generate variants independently from text and never feed the preceding time of day into the next one: repeated edits accumulate drift.

Inspect local input images before editing. Supply the original master in OpenRouter's `input_references` using a provider-accessible HTTPS URL or a base64 data URL within the request-size limit, as described in [references/openrouter.md](references/openrouter.md). A local path or conversation attachment is not an API reference. Send the same original master and native 4K resolution/aspect-ratio settings on every edit and retry, and require the output to match the measured master dimensions. If that reference is no longer accessible, restore it before continuing. Never invent unsupported seed, mask, strength, or fidelity parameters, and never treat a repeated seed as a geometry guarantee.

Reuse the same invariant prompt verbatim, changing only the lighting specification. Allow exposure, color temperature, sky illumination, physically coherent shadows, highlights, and illumination of existing fixtures. Sun, moon, and stars may change visibility/position only according to the scene plan; they must not cause scene rearrangement. Keep the original art style and level of detail.

Save each output as a separate full-resolution PNG. Check each frame against the master before continuing, so a failed method does not produce an entire unusable set. If a frame fails the perceptual acceptance standard, retry from the original master with a precise description of the distracting change. Default to at most two retries per failed frame. If it still fails, preserve accepted work, explain the remaining mismatch, and stop before producing a final wallpaper. Do not silently lower the agreed standard or retry an otherwise acceptable frame solely for tiny native-size differences.

Apply the same check and retry limit to lighting failures. In particular, Nano Banana may retain the master's cast shadows while changing only exposure and colour. Where the scene plan requires shadow movement or a different illuminated face, reject an edit that retains the old lighting pattern; name the affected lighting landmarks in the retry. Geometry preservation does not require preserving cast-shadow boundaries.

## Review the entire set

The bundled `scripts/review_wallpaper.py` checks the time manifest and PNG header dimensions, and creates a local comparison page. Its optional `--export-overlays` mode uses ImageMagick to create full-frame overlays, native-size tiles and neighboring-time comparisons in a fresh directory. These are inspection aids; accepted source images are never altered and no visual pass is assigned. Read [references/daynight.md](references/daynight.md) for the manifest and commands.

Inspect actual rendered images, not just filenames, tool success, or a thumbnail contact sheet:

1. Compare every frame with the master at normal desktop size, including corners and detailed landmarks, and inspect transitions at that scale. Use overlays or blink and selected 100% crops to diagnose doubled contours, changed counts, shifted textures, new objects, missing details, crop, scale, perspective, or horizon movement. Assess whether a difference distracts in the whole image or transition before rejecting it; native-size differences alone are not automatic failures. A global similarity score cannot certify this under changing illumination.
2. Separate expected light/shadow boundaries from object boundaries. Reflections may brighten or change color; reflected objects must still have the same structure and placement. Darkness is not evidence that hidden geometry matches. Mark regions that cannot be assessed as uncertain rather than passed.
3. Compare neighboring times and the last-to-first transition. Look for scene jumps, style changes, inconsistent light direction, flickering cloud shapes, or unrelated weather changes. Keep nighttime readable without making it look like daylight tinted blue.
4. Check sun direction and shadow progression separately from geometry. Compare morning, noon and sunset at full frame and the selected lighting landmarks at 100% zoom. Check cast-shadow direction and length, illuminated versus shaded faces, and mountain/terrain occlusion against the recorded plan. A warmer sunset or a coherent shadow field within one image does not prove the planned sun movement. Dawn and blue hour should lose direct-sun shadows where the plan places the sun below the local horizon; assess moonlight separately at night. If diffuse light or occlusion hides the evidence, record that limitation as `uncertain` rather than inventing a pass.
5. Record each frame's inspected landmarks, hash, review display/preview dimensions, separate geometry and sun/shadow results (`pass`, `fail`, or `uncertain`), expected versus observed lighting evidence, and any unresolved mismatch in `review.md`. A geometry pass means no distracting drift at the reviewed desktop scale; list any accepted minor differences separately. Re-review replacements. Do not mark frames passed without opening them or use an “artistic” label to excuse a contradiction with the chosen sun path. Only package a set whose required checks pass; otherwise explain what remains unverified. An explicit user acceptance of a known lighting limitation may be recorded as an exception for that set, without weakening future checks.

Use the comparison page in a browser if available. If browser interaction is unavailable, inspect the files directly with available image tools and state the reduced review coverage. Do not invent a completed blink/overlay review. An unperformed required check remains unfinished.

Render inspection images in small batches so tool output limits do not omit them. Save each frame's review result before proceeding; an exported or omitted image is not an inspected image.

## Package and deliver

For macOS, follow [references/daynight.md](references/daynight.md): validate the accepted frame set, produce the time-based manifest, build the HEIC with daynight, then run `scripts/verify_wallpaper.py` to decode every frame and check dimensions, schedule and appearance indices. Open its primary/Light/Dark previews to confirm their visual assignments. The reference also covers recovery from restricted macOS image-service access. Do not change the desktop wallpaper unless asked.

For other platforms, deliver the accepted PNGs and requested schedule format; do not claim an unsupported native dynamic-wallpaper package exists. If the HEIC encoder is unavailable, deliver the PNGs, manifest, review, and exact packaging command, clearly marking HEIC generation incomplete.

When working in the daynight repository, also copy each finished, reviewed and verified set into its GitHub Pages gallery with `scripts/add_wallpaper.py` at the repository root. Follow the [gallery delivery instructions](references/daynight.md#github-pages-gallery). Keep original downloads unchanged and copy only accepted frames. Updating the local gallery is part of delivery; publishing commits to GitHub requires authorization from the current task.

Return links to the final files and comparison page, actual resolution and frame count, and a short account of visual review and packaging validation. Distinguish successful HEIC encoding from observing real macOS wallpaper switching. Include known limitations, accepted minor drift, review scale and the saved prompt set. Use wording such as “no distracting drift found at the reviewed desktop scale,” never “guaranteed identical.”
